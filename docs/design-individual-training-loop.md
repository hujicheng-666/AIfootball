## 0. 设计基线

本设计建立在这几条已确认的结论之上（来自可行性分析）：

1. **个体化模型**：每个射手一个模型，彻底绕开文献中"跨被试泛化差"这个最大的技术风险。
2. **用户自己训练**：训练必须能在用户机器上完成，因此模型必须是轻量关键点序列模型（CPU 可训）。
3. **本地 + 云端两级训练**：同一套训练代码 + 规模参数化，产出一致的模型格式；不做两套系统。
4. **数据必须来自真实踢球**：门将的起扑方向由模型预测控制，后续移动仍由现有趋近算法负责。
5. **核心验收指标是扑救率**（目标 18%–30%），不是模型准确率。

## 1. 总览与用户旅程

### 1.1 闭环（用户视角只有 5 步）

```
①建档        ②采集             ③训练            ④启用         ⑤持续提升
建射手档案 → 踢 ~50 次     →  本地快训(CPU)  → 门将用 v1   → 再采再训
            自动打标签        分钟级出 v1      扑救率立刻变  目标 300+ → 云端精训
                            ↑                                    │
                            └──────────── 数据持续累积 ───────────┘
```

**关键前提：用户全程不需要标注任何数据。** 标签由现有双目重建的球落点自动生成。这是整个闭环能成立的基础——如果标注需要人工介入，用户不会坚持到 300 次。

### 1.2 组件与复用关系

| 组件 | 职责 | 现有可复用 | 需新建 |
|---|---|---|---|
| 射手档案 | 身份、数据集归属、模型版本 | `ShooterProfileAnalyzer`（**要改语义**：从"全局统计"改为"按射手"） | 档案存储、模型版本表 |
| 采集服务 | 预滚动落盘、逐帧时间戳、第三路取流 | `DualCameraRecorder`、`FrameClock`（已写好未接线）、`deque(300)` | 第三路、预滚动、时间戳落盘 |
| 自动标注器 | 球轨迹 → 真实落点 → 3×3 网格标签 | `reconstruct_3d_trajectory`、`fit_ballistic_trajectory` | 落点→网格映射、标签置信度 |
| 数据质检门 | 拒绝垃圾样本（关键点丢失、光照、标签矛盾） | 现有质量指标（`ray_gap`、重投影误差） | 关键点覆盖率与连续性检查 |
| 训练流水线 | 特征 → 模型 → 校准 → 评估 | 无 | 全新。**本地与云端同一套代码，规模参数化** |
| 预测服务 | 加载模型 → 输出落点概率分布 | 无 | 全新。**无模型时走 C1 兜底** |
| 仿真集成 | 预测 → 门将起扑 | `TendGoalMainState`、`InterceptShotMainState` | 预测字段 + 反应延迟 |

### 1.3 数据流

```
踢球 → 三路录制（含触球前 3 秒预滚动）
   ├─ 球轨迹重建 ──────► 真实落点 ──► 3×3 网格标签（自动）
   └─ 姿态估计(裁剪ROI) ─► 关节序列 ──► 只保留 t < t_kick − Δt 的帧
                                    │
              特征(坐标+速度+角度) ─┴─► 训练/增量更新 → 校准 → 时间截断评估
                                                    │
                                             模型版本入库 → 下次回放自动启用
```

### 1.4 三个不可协商的约束

1. **预滚动是硬前提**：现在录制从点击才开始，`LEAD_IN` 只有 0.3 秒，模型看不到助跑。必须先修。
2. **只保留 `t < t_kick − Δt` 的帧**：防标签泄漏的闸门。放开会让准确率虚高到 95%+，门将又变回"每次扑对"。
3. **冷启动必须有兜底**：没有模型时用可行性分析里的 C1"观测降级"行为，否则用户第一次打开看到的是一个依然 100% 正确的门将。

## 2. 数据策略

> 本节解决一个现实问题：**当前可用训练数据为 0**（`samples/` 里 3 段实拍是球场走动测试，`data/*.csv` 是合成直线数据）。在用户还没有踢过一次球的前提下，如何让闭环跑起来。

### 2.1 调研结论：能拿到的公开数据

| 数据集 | 内容 | 许可 | 可用性 |
|---|---|---|---|
| **[3D Shot Posture (3DSP)](https://github.com/calvinyeungck/3D-Shot-Posture-Dataset)**<br>CVPR 2024 Workshop (CVsports) | **200 个职业球员射门**（train）× 20 帧裁剪图；每帧含**人工标注的 2D 关键点** + **MotionAGFormer 提升的 3D 关键点** + tracklet（MOT20 格式）；test 集 10 个 shot | **Apache 2.0** | ✅ **可商用**，`git clone` 即得，无需申请 |
| [SoccerNet](https://www.soccer-net.org/) | 500 场完整比赛转播 + 17 类动作标注（含 Penalty）；3DSP 的数据来源 | 需签学术协议 | ⚠️ 可用于把点球样本扩到几千个片段 |
| [SportsPose](https://christianingwersen.github.io/SportsPose/) | 24 名受试者 × 191,948 个 3D 姿态 × 5 种运动（**含 soccer**）；7 相机硬件同步 90Hz；与商业动捕对比误差 **34.5 mm**；CVPR 2023 Workshop **Best Paper** | **仅限学术用途**（需学术邮箱申请） | ❌ **商用不可用**，只能作研究对照 |

**3DSP 是被低估的资产**：它不只给数据，还给完整工具链——YOLOv8 + BoT-Sort 跟踪、MotionAGFormer（2D→3D 提升）、可视化、预处理，甚至包含从 SoccerNet 下载并标注新片段（`dataset_annotation.py`）的脚本。

它的 `info.ini` 提供：`label`（**shot on target / off target**）、`annotated_position`（动作毫秒）、`shooter_tracklet_id`、`visibility`、`game`、`half`。

### 2.2 核心障碍：没有任何公开数据集有"射门方向"标签

已逐一核查：

- **3DSP** 只有"射正/射偏"，**没有左/中/右**；
- **SportsPose** 是实验室采集的动作，**根本没有球门**；
- 可行性分析中引用的 [arXiv:2509.26088](https://arxiv.org/abs/2509.26088) 的 755 个点球事件是作者**自建、未公开**；
- [NOLTA 的 ESN 研究](https://www.jstage.jst.go.jp/article/nolta/17/3/17_1079/_article/-char/en)的 4 人数据同样未公开。

**结论：不存在"下载数据集直接训练方向分类器"这条路。** 标签问题无法靠"找"解决。

### 2.3 解法：合成数据路线

既然找不到标签，就自己造——而且这条路有硬证据支撑：

> **[Avatar4D / Syn2Sport](https://ar5iv.labs.arxiv.org/html/2512.16199)**（University of Waterloo, 2025）证明：在**真实域**上，加入合成体育数据后姿态估计 AP5 提升 **55.96%（棒球，29.3→45.7）** 与 **114.5%（冰球，13.1→28.1）**；且棒球合成的模型能**零样本迁移到真实足球**数据集；合成数据与真实数据的 FID 为 14.3（对比同类 SportPAL 的 21.6）。

**生成方法（不依赖任何付费/受限资源）：**

```
3DSP 的 200 个真实射门 3D 骨骼序列        ← 最难得的资产：真人职业球员的动作
        │
        ├─ ① 运动学参数化
        │     在髋/躯干施加旋转、改变支撑脚朝向与助跑角 → 生成"不同方向"的样本
        │     标签 = 施加的旋转量（完美、精确、免费）
        │
        ├─ ② 域随机化（关键，否则合成数据无用）
        │     关键点噪声 / 时间抖动 / 丢帧 / 关节交换 / 体型缩放 / 视角扰动
        │     目的：让合成骨骼在统计上接近真实检测器的输出（而非理想骨架）
        │
        └─► ③ 产出：几千 ~ 几万个【带完美方向标签的骨骼序列】→ 预训练
                                            │
                            自有采集 50 次  →  微调  →  可用模型
```

**为什么这条路成立**：模型输入是**归一化骨骼坐标**（以髋为中心、按身高缩放），不是像素。骨骼表示天然具有跨域不变性，域间隙远小于 RGB 图像。Avatar4D 用更难的 RGB 路线都成功了。

**一个重要简化**：因为输入只需骨骼，我们**不需要渲染、不需要 3D 资产、不需要 3D Gaussian Splatting**——直接在 3D 骨骼空间做参数化变形即可。这让合成流水线从"一个研究项目"降级为"一个脚本"。

### 2.4 三层数据策略

| 层 | 数据 | 作用 | 成本 | 归属 |
|---|---|---|---|---|
| **L1 合成预训练** | 3DSP 骨骼 + 参数化变形（数千~数万序列） | 解决冷启动，让 50 次微调就有好效果 | **0 元**，无版权风险 | 全局共享 |
| **L2 公开真实数据** | 3DSP 的 200 个真实样本；（可选）SoccerNet 扩展 | 验证"合成→真实"迁移是否真的有效；真实域校准 | 0 元（SoccerNet 需协议） | 全局共享 |
| **L3 自有采集** | 用户真实踢球 50 → 300+ 次 | 微调出最终个体化模型 | 约半天 / 人 | **射手私有** |

**关键架构含义**：L1/L2 训练出的是**全局预训练基座**（所有用户共享，随产品迭代版本化）；L3 训练出的是**射手私有微调模型**。因此模型管理要区分"基座版本"与"射手模型版本"两级，射手档案只持有对基座版本的引用 + 自己的微调权重。

### 2.5 必须做的验证实验（决定 L1 是否值得投入）

合成预训练到底有没有用，**必须用实验回答，不能假设**。低成本消融：

| 组 | 训练方式 | 预期 |
|---|---|---|
| A | 只用自有 50 次数据训练 | 基线准确率 |
| B | 合成预训练（L1）→ 自有 50 次微调 | 应显著优于 A |
| C（可选） | 3DSP 真实样本预训练 → 自有 50 次微调 | 上界参考 |

**决策门**：若 B 相对 A 没有显著提升，则放弃 L1，把资源全部投入到更多自有采集。这个实验成本很低（一个脚本 + 一次训练），应放在 P0 阶段与可行性分析中的 C1/C2 实验并行。

### 2.6 两个明确的坑

**坑 1：Mixamo 不可用。** 本来"用免费踢球动画做合成数据"是最自然的想法，但 [Adobe 官方 FAQ](https://helpx.adobe.com/creative-cloud/faq/mixamo-faq.html) 明确：Mixamo **不适用于中国区账号**（Creative Cloud 中国版不含 web 服务）。好消息是**不需要它**——3DSP 那 200 个真实射门骨骼比任何通用踢球动画都更贴近真实点球动作。

**坑 2：不要把"爬取"当主力。** 从公开视频（YouTube 点球集锦等）爬取技术可行，但：① 版权合规风险；② 转播远景机位与项目固定机位近景的域间隙很大；③ 清洗与标注成本可能高于采集成本。**爬取最多只用于预训练，绝不能替代 L3 自有采集。**

## 3. 零采集验证实验（P0，立即执行）〔已确认〕

> **决策**：先不自采数据，用公开数据集把技术链路跑通，看姿态里到底有多少方向信号。**验证通过再投入采集与硬件。**

**目标**：在**零采集成本**下回答一个问题——"从触球前的人体姿态，能不能以显著高于随机的水平预测射门方向？"

**这次实验看不到什么（必须提前明确）**：离线准确率与提前量曲线可以看到；**门将扑救率的变化看不到**——公开数据的骨骼不是本项目相机拍的，且仿真里没有射手角色。端到端效果只有采了自有数据才能测。

### 3.1 数据获取

```bash
git clone https://github.com/calvinyeungck/3D-Shot-Posture-Dataset.git
cd 3D-Shot-Posture-Dataset
unzip 3dsp.zip          # 数据随仓库分发，无需申请；License: Apache 2.0
```

- **训练集**：200 个 shot × 20 张裁剪图 + H3WB 格式 JSON（2D + 3D 关键点）+ MOT20 tracklet + `info.ini`
- **测试集**：10 个 shot
- 可选工具链（仓库自带）：YOLOv8 + BoT-Sort（跟踪）、MotionAGFormer（2D→3D 提升）、`vis_post.py`（可视化）、`pre_process.py`（预处理）

### 3.2 数据勘察结果（已执行 2026-09-30）

**结论：3DSP 可以用，但有一个会改变实验设计的硬限制。**

| 勘察项 | 实测结果 | 判定 |
|---|---|---|
| 规模 | train **200** + test **10** = 210 个 shot，来自 **22 场比赛** | 够做验证，不够训产品模型 |
| 标签 | **只有"射正(115) / 射偏(95)"** | ❌ **无方向标签** |
| 关键点 | 17 关节（H3WB 格式），2D（100×100 归一化）+ 3D | ✅ |
| 姿态质量 | 200 shot × 20 帧 × 17 关节，**缺失率 0**（全部非零） | ✅ 质量优秀 |
| 时序结构 | 总跨度 **600 ms**（210 个样本完全一致）；`annotated_position` 恒为 `start_position + 500 ms` | ✅ 极其规整 |
| **触球帧** | 用踝关节速度峰值定位：**中位数第 14 帧**，64.5% 落在第 13–16 帧 | ✅ **触球前约 15 帧** |
| 可用提前量 | 触球前 15 帧 ÷ 帧间隔（31.6ms 或 40ms）≈ **470–600 ms** | ✅ 支持 Δt ∈ {0,100,200,300,400} ms |
| 图像分辨率 | **仅 100×100 px** | ❌ **RGB 多模态路线不可行** |
| 关节覆盖 | **无脚部关节**（只有 Ankle，无 foot/toe） | ⚠️ 测不了"支撑脚指向"这一强特征 |
| test 集 | **无 `posture` 目录**，需自行提取姿态（YOLO11n-pose 处理 10×20=200 帧约 15 秒） | ⚠️ 独立测试集仅 10 个样本 |

**关节清单**（H3WB 17 点）：`Center of Hips` / `Left Hip` / `Left Knee` / `Left Ankle` / `Right Hip` / `Right Knee` / `Right Ankle` / `Center of Body` / `Center of Shoulder` / `Neck` / `Head` / `Right Shoulder` / `Right Elbow` / `Right Wrist` / `Left Shoulder` / `Left Elbow` / `Left Wrist`

#### ⭐ 由此暴露的关键问题

**3DSP 没有方向标签**，因此原设计的"实验组 2（合成训练 → 真实骨骼测试）"**无法用方向标签评估**。3DSP 的角色只能是：

1. **运动源**（合成数据的真实骨骼基础）—— 仍是最有价值的用途；
2. **姿态表示可迁移性的验证集**（改用射偏/射正做下游二分类）；
3. 若要真正验证方向预测，必须 **自采哪怕 30–50 次数据（半天）**，或人工为 3DSP 标注方向（需先按 `info.ini` 的 `game`/`half`/`gametime` 定位原始比赛视频）。

> 这一点必须明确：**"完全不采集数据就能看到方向预测效果"是不成立的**。零成本能得到的是"架构能否学到 + 姿态表示能否迁移"；真实的端到端方向效果，最低成本是半天自采。

### 3.3 合成数据生成

**核心思路**：不凭空造动作，而是**以 3DSP 的真实 3D 骨骼为运动源**，施加物理合理的小幅参数化变形，变形量本身就是精确标签。

```
3DSP 的 200 个真实射门骨骼序列（职业球员，真人动作）
        │
        ├─ ① 参数化变形（标签来源）
        │     髋/骨盆绕垂直轴旋转、支撑脚位置与朝向调整、摆腿平面偏移
        │     每个真实序列 → 生成 N 个变体（如 N=50）→ 约 1 万条带标签序列
        │
        ├─ ② 域随机化（必须，否则合成数据无用）
        │     关键点高斯噪声(σ≈实测检测误差 ±3~5px) / 时间抖动 / 丢帧与关节丢失
        │     / 左右腿关节交换（真实检测器常见错误）/ 体型缩放 / 视角微扰
        │
        └─► ③ 标签 = 施加的变形方向（精确、免费、可任意控制分布）
```

**⚠️ 最大的技术风险：捷径学习（shortcut learning）。** 如果变形只作用在单一关节上，模型会直接学会"检测那个旋转量"，而不是学真实的生物力学线索——**在合成数据上准确率很高，迁到真实数据就崩**。对策：

1. 变形必须**多关节组合**（髋 + 支撑脚 + 摆腿平面），且组合权重随机化；
2. 变形幅度必须落在**真实解剖学范围内**；
3. **必须靠实验组 2（合成训练 → 真实测试）来暴露它**，不能只看合成测试集的高分。

### 3.4 实验设计（据勘察结果修正）

| 组 | 训练数据 | 测试数据 | 标签来源 | 回答的问题 | 成本 |
|---|---|---|---|---|---|
| **1** | 合成 | 合成（留出） | 施加的变形量 | 架构能否学到东西（性能上限） | 0 |
| **1b** | 合成（关闭域随机化） | 合成 | 同上 | **消融：域随机化是否必要**（直接暴露捷径学习） | 0 |
| **2** | 合成 | **3DSP 真实骨骼** | ⚠️ 无方向标签 → **改用"射正/射偏"二分类** | 合成预训练是否学到**可迁移的姿态表示** | 0 |
| **3** | 自采 30–50 次（留出法） | 同 | 真实落点（自动标注） | **真正的方向预测效果** | 半天 |

**成功判据（现在就定，避免事后自欺）**：

- **组 1**：合成测试集三分类准确率显著 > 33%（说明架构有效，但**不能证明有用**）；
- **组 1b**：关闭域随机化后准确率显著下降 → 说明模型确实在依赖域随机化覆盖的真实误差，而非捷径；若两者相同，**说明模型学到的是捷径**，必须回头改变形策略；
- **组 2**：预训练 vs 随机初始化的二分类 AUC 提升 → 迁移成立；
- **组 3**：方向三分类准确率显著 > 33%（建议阈值 ≥50%，附置信区间与混淆矩阵），并绘制"准确率-提前量曲线"（Δt ∈ {0,100,200,300,400} ms，曲线应单调下降，否则排查标签泄漏）。

**评估指标**：主指标用 **log loss / ECE（校准误差）**，而非只看 accuracy——下游门将需要的是概率分布，不是 argmax 方向（见可行性分析 §4 风险 4）。

### 3.5 产出与后续决策

| 产出 | 状态 | 用途 |
|---|---|---|
| 数据勘察报告 | ✅ **已完成**（见 3.2） | 确认 3DSP 可用性、触球帧与最大提前量；暴露"无方向标签"限制 |
| 合成数据生成脚本 + 数据集 | 待做 | **可复用资产**：将来用户微调的预训练基座数据来源 |

## 4. 采集闭环〔设计已确认，实施排在 P0 之后〕

### 4.1 预滚动：现有实现不能直接扩展

`camera_capture.py:189` 的 `deque(maxlen=300)` 存的是**全分辨率原始帧**（`frame.copy()`）。3264×1440×3 字节 = **14.1 MB/帧**，300 帧 = **4.2 GB/路**，三路 = **12.6 GB**。"把环形缓冲落盘"本质上不可行。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 分段录制（选定）** | 每次踢球单独触发一段（含助跑），按 `t_kick` 裁窗口 | 简单可靠，无内存风险 | 无效数据占磁盘 |
| B 编码后环形缓冲 | 后台线程把帧编码写入循环覆盖的临时段 | 省磁盘 | 复杂，编码抖动丢帧 |
| C 低分辨率预滚动 | 预滚动段降采样，正式段全分辨率 | 折中 | **姿态精度受损**（腿部 150px → 44px，正好抵消第三路相机的价值） |

**交互流程重构（方案 A 的落地形式）**：

```
现在：点"开始分析" → 连踢很多球 → 点"停止" → 事后找 kick_frame 切
改为：点"开始这一球" → 自动录 10 秒（覆盖助跑+踢球+飞行）→ 自动停 → 自动质检+打标
```

每次踢球产生一个独立、完整、干净的样本，`t_kick` 前后窗口天然对齐。

### 4.2 三路对齐

`FrameClock`（含 PTS 单位推断）**已实现、未接线**——接线即得逐帧时间戳。叠加一个共享视觉事件（手机屏闪 / LED / 拍手）做互相关校准，目标 **<10 ms**。这是 P0 必须偿还的既有债务。

### 4.3 质检门（四道，全自动）

| 门 | 判据 | 不合格时 |
|---|---|---|
| 关键点覆盖 | `[t_kick−1.5s, t_kick]` 内踢球者检出率 ≥90%，膝/踝置信度达阈值 | 提示"构图问题"，**必须给出原因** |
| 球的轨迹 | 复用现有 `ray_gap`、重投影误差指标 | 丢弃该球 |
| 标签有效 | 落点可映射到 3×3 网格（或明确记为射偏） | 标记"无标签"，不进训练集 |
| 窗口完整 | 预滚动段未被截断 | 丢弃 |

**拒绝时必须告知用户原因**（"踢球者不在画面内"/"腿部被遮挡"），否则用户只会认为软件故障，而不知道是相机歪了。

### 4.4 采集引导策略

**是否指导用户踢向指定方向**，直接决定数据性质：

| 策略 | 后果 |
|---|---|
| 指导（"这球踢左上"） | 9 宫格分布均衡，但用户会**刻意演动作**，模型学到"表演"而非真实习惯 |
| 不指导 | 动作真实，但业余用户会习惯性偏一侧，训练集严重偏斜 |
| **折中（选定）** | 向导显示"当前 3×3 覆盖度"与"建议尝试区域"，**但不强制**；**标签永远来自球的真实落点**，与用户是否听从无关 |
